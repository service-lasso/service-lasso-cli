## Exact authority attribution and bounded constructor proposal

D7A (cli39-prerequisite-windows-tool-trust-method-20261010.md), paragraph beginning “The source unit must bind”, requires actual verifier API/provider modules, OS/policy/version, trust anchors/store identity and applicable snapshot/lifetime, independently established expected upstream publisher identity, signature subject and trusted timestamp/current validation policy, revocation disposition and original results. EF52 (prerequisite-tool-authentication-and-budget-boundary-20261010.md), first substantive paragraph, requires the finite trust-anchor chain, revocation/time/policy, exact subjects, validation outputs and useful supported behavior. OWNER-CONSUMERS26 Windows worker paragraphs73-75 require complete original provider/signer/certificate/timestamp capture and preserve cache-only limitations. These clauses require evidence relations, not four separately issued receipt files. The current receipt-shaped source encoding must not become an additional file-count/issuer prerequisite.

The existing trust foundation is the independently admitted Windows host/OS policy and selected existing signed distribution under D7A, with actual held verifier/provider/loaded module originals owned by the SAME root/receiver. This proposal does not replace it with a new external policy issuer. Its authenticity is a genuine input-review obligation; current selectors or raw observations do not supply it.

Proposed fixed constructor sequence within that ownership model:

1. Enroll a once-only policy-join original under SAME publisher preparation before allocating its rows. Bind SAME root policy, SAME publisher/expected-certificate held originals, SAME root native association, SAME Wintrust module/initialization/verify originals, original deadline and complete consumer reservation. This constructor must run only after the real root association constructor has enrolled its actual independently admitted OS/policy/loaded-source inputs; a caller-provided authority boolean is forbidden.
2. Retain the exact selected default Authenticode API/action/flags and actual copied provider results; require actual raw verification terminal result and a complete supported raw graph. Each failed/null/unsupported actual relation remains distinct, never a successful policy assertion. This establishes observed native outcomes only.
3. Join actual expected-leaf DER byte comparison to the independently admitted upstream publisher/certificate association in the root input ownership graph. Expected identity comes from that admitted input, never the candidate's own name. Exact expected-certificate bytes plus subject signature result remain individually retained.
4. Join copied provider store/chain roots and signature time/revocation outputs to the actual admitted OS policy/store snapshot and selected validation-time/revocation disposition. Preserve actual certificate and chain association results, including unmatched/absent/failure. Current cache-only operation can succeed usefully only when the genuine admitted policy/evidence establishes the applicable disposition; it cannot manufacture fresh revocation from cached status.

Only all actual required positive joins can publish useful acceptance. Provider capture custody and destruction eligibility remain separate original obligations.
